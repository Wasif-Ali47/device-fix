User Authentication APIs – Deep Validation & Error Handling

1. SIGNUP API

Endpoint: POST /auth/signup

Request Body:

{ fullName, email, password, profileImage (file) }

Validation Flow (Execution Order)

  • Step 1: If fullName, email, or password is missing
    → Response: 400 { "error": "All fields required" }
  • Step 2: If email is not valid (example: abc@, abc.com)
    → Response: 400 { "error": "Invalid email format" }
  • Step 3: If password.length < 6
    → Response: 400 { "error": "Password must be at least 6 characters" }
  • Step 4: If email already exists in database
    → Response: 400 { "error": "User exists" }

Success Response

200 → { "message": "Signup successful, verify OTP", "userId": "USER_ID" }

Frontend Note: OTP screen sirf is response ke baad open karni hai.

2. VERIFY OTP

Endpoint: POST /auth/verify-otp

Request Body:

{ userId, otp }

Validation Flow

  • Step 1: If userId OR otp missing
    → 400 { "error": "User ID and OTP required" }
  • Step 2: If userId is not valid MongoDB ObjectId
    → 400 { "error": "Invalid user ID" }
  • Step 3: If OTP is not exactly 6 digits
    → 400 { "error": "Invalid OTP format" }
  • Step 4: If OTP does not match stored OTP
    → 400 { "error": "Invalid OTP" }

Success

200 → { "message": "Email verified" }

3. LOGIN API (DETAILED VALIDATIONS)

Endpoint: POST /api/auth/login

Request Body:

{ email, password }

Validation Execution Order (IMPORTANT)

  • Step 1: Missing Fields
    Condition: email OR password missing
    → 400 { "error": "Email and password required" }
    Frontend: Show inline validation, don’t hit API if possible

  • Step 2: Invalid Email Format
    Condition: Email does not match regex (abc@, abc.com, etc.)
    → 400 { "error": "Invalid email format" }
    Frontend: Validate on blur / submit

  • Step 3: Email Not Registered
    Condition: Email not found in database
    → 400 { "error": "Email not registered" }
    Frontend: Suggest “Sign up” CTA

  • Step 4: Password Incorrect
    Condition: Email exists BUT password mismatch
    → 400 { "error": "Password incorrect" }
    Frontend: Show “Forgot password?” link

  • Step 5: Email Not Verified
    Condition: Correct email + password BUT emailVerified === false
    → 400 { "error": "Email not verified" }
    Frontend: Redirect to OTP verification screen

Success Response

200 → { "token": "JWT_TOKEN" }

Frontend Handling Rules:

  • Save token only on success
  • Do NOT store token if any error occurs
  • Error message should be shown EXACTLY as received

6. FORGOT PASSWORD

  • Email missing → 400 { "error": "Email required" }
  • Invalid email → 400 { "error": "Invalid email format" }
  • User not found → 404 { "error": "User not found" }
200 → { "message": "OTP sent" }

7. RESET PASSWORD

  • Any field missing → 400 { "error": "All fields required" }
  • OTP not 6 digits → 400 { "error": "Invalid OTP format" }
  • Password < 6 chars → 400 { "error": "Password must be at least 6 characters" }
  • OTP incorrect → 400 { "error": "Invalid OTP" }
200 → { "message": "Password reset successful" }
